# Архитектура небольшой браузерной игры

Это рекомендации для роста каркаса, а не список уже созданных подсистем. Текущие точки расширения: `src/main.js`, `src/loop.js`, `src/input.js`, `src/scene.js`. Происхождение выводов — в [sources](sources.md).

## Владельцы и зависимости

Начни с одной играбельной сцены. Выделяй модуль, когда у него появляется самостоятельное состояние, контракт или причина меняться. Разделение по ответственности полезнее заранее созданной иерархии классов.

| Ответственность | Владелец при расширении | Контракт |
| --- | --- | --- |
| Сборка приложения и связь подсистем | `main` | Создаёт зависимости, соединяет их и освобождает приложение |
| Шаг времени | `loop` | Вызывает fixed update, ограничивает догоняние, выдаёт alpha |
| Устройства ввода | `input` | Переводит события в намерение игрока, очищает удержания |
| Правила и состояние уровня | `scene` или gameplay-модули | Update/reset; логика проверяется без DOM и WebGL, где возможно |
| Физический мир | Один runtime симуляции, если нужна физика | Регистрация тел, один шаг мира, синхронизация после шага |
| Модель, камера, эффекты | Presentation-модули по мере роста | Отображают состояние, владеют своими визуальными ресурсами |
| Загрузка и общие ассеты | Resource owner, если появилось совместное использование | Кэш, ошибки/retry, последний владелец освобождает ресурс |
| Панели и настройки | UI | Команды игре и отображение snapshot; не отдельная копия игрового состояния |

Передавай необходимые зависимости явно. Маленькому проекту достаточно функций и объектов с понятным API. ECS, event bus, singleton и отдельный framework выбирай под конкретную проблему. События полезны для завершённых фактов (`impact`, `level-complete`); управление непрерывным шагом проще видеть в явном вызове.

## Порядок кадра и единицы

```text
RAF, секунды с прошлого кадра
  → 0..maxSteps фиксированных тиков:
      ввод и намерения → контроллеры/силы → один шаг мира → post-step
  → позы previous/current с alpha
  → камера по отображаемой позе
  → визуальные эффекты и подготовка GPU-буферов
  → render и обновление UI по необходимости
```

Без физики fixed update просто обновляет правила игры. Движок рендера не задаёт частоту симуляции. Каркас сейчас использует шаг `1/60` секунды и максимум 8 шагов за кадр; CarWars использует другие значения. Меняй их по механике и проверкам, а не по названию движка.

Выбери единицы мира, оси, направление вперёд и значение углов. Например, для 3D удобно записать «метры, секунды, радианы, Y вверх, игровой forward +Z»; forward модели может отличаться и исправляется её визуальным pivot. Перевод screen → world выполняется в одном месте. Не смешивай скорость в м/с с UI в км/ч, локальную позицию с мировой и реальное время с игровым.

`previous/current` принадлежат симуляции. Интерполяция меняет только графику; камера следует за той же позой. При spawn/reset/перемещении уровня обе позы совпадают, иначе появится пролёт из старой точки. Для ориентации используй кратчайшую дугу или quaternion slerp. Плавность камеры с коэффициентом `1 - exp(-rate * dt)` учитывает время кадра.

Если тела должны сталкиваться, у них общий физический мир. За fixed tick один владелец готовит все силы, один раз вызывает шаг мира и выполняет post-step для всех тел. NPC-контроллер выдаёт steer/throttle/brake или другое намерение; он не интегрирует мир повторно. Декоративный tween не определяет контакты и урон. Прямое изменение физической позы допускается только явно выбранной политикой spawn/reset/teleport.

## Состояния и lifecycle

По потребности добавляй `loading → playing → paused/game-over`, `loading → error → retry`, `game-over → restart`. У перехода есть инициатор, условия и очистка предыдущего состояния. Не разрешай игру до готовности обязательных ресурсов; необязательные декорации могут догружаться отдельно.

В текущем каркасе `scene` имеет `update/render/reset/snapshot/dispose`. Сохраняй смысл контракта при добавлении движка; менять сигнатуру render можно вместе с вызывающим кодом. Render не меняет правила игры, но может обновлять визуальные буферы и состояние эффекта. Snapshot возвращает данные, а не ссылки для произвольной записи в runtime.

- Pause, hidden и reset очищают accumulator и удерживаемый ввод. Blur/pointercancel также освобождают управление.
- Reset возвращает игровое состояние к выбранному началу. Он очищает скорости, предыдущие позы, цели, reservations и callbacks, относящиеся к прошлой попытке.
- Dispose останавливает RAF/таймеры, удаляет listeners, отменяет работу сцены и освобождает только принадлежащие ей ресурсы. Повторная очистка должна быть безопасной по выбранному контракту.
- Для асинхронной загрузки держи generation/request ID. После смены сцены результат старого запроса не подключается; его ресурсы освобождает владелец. Abort применяй только там, где загрузчик его поддерживает.

## Несколько ролей NPC

Когда появляется вторая роль, отдели общие регистрацию, occupancy, шаг мира и удаление от политики поведения. Роль определяет намерение и визуальное оформление; runtime сохраняет единый список акторов и общие ограничения. Это вывод из гражданского трафика и полиции CarWars, применимый к врагам, союзникам и другим взаимодействующим объектам.

Используй стабильный actor ID. Резервирование пути/места связано с ID и имеет правила освобождения при завершении, удалении, reset и смене карты. Реестр и пространственный индекс описывают один и тот же набор акторов. Решения нескольких NPC удобно готовить по согласованному снимку occupancy, затем явно разрешать конфликтующие заявки; порядок обхода массива не должен скрыто давать вечный приоритет одному участнику.

Безопасный спавн проверяет конечные координаты, bounds, высоту поверхности, статические препятствия и реальные габариты с поворотом. Проверка одного центра недостаточна. Результат может быть структурированным: `created` с ID и позой, `pending` с request ID и причиной или `rejected` с причиной. Поиск ближайшей безопасной точки — явная политика; он не должен молча подменять точный запрос. Очередь имеет ограниченный бюджет, отмену и правила смены карты.

LOD графики и LOD симуляции различаются. Скрытие mesh само по себе не останавливает update. Упрощённый дальний актор сохраняет маршрут, ID и необходимую occupancy; контакт с игроком требует подходящего представления. Переходы используют запас расстояния/гистерезис и проверяются на обоих направлениях. Настройка качества изображения не должна менять победу, урон или правила столкновений.

Безопасность и прогресс проверяются отдельно: «нет пересечений» не доказывает «все NPC продолжают движение». Для остановки сохраняй причину, blocker ID, длительность, цель и фактический прогресс. Recovery выбирает безопасный повтор/перепланирование и имеет пределы; повышение мощности или скрытый перенос актора не объясняет deadlock. Сценарий должен проверять каждого актора, а не только общую пройденную дистанцию.

## Карта мира и параметры

У процедурного уровня один источник данных для визуальной геометрии, навигации, коллайдеров и surface-height sampling. Декоративная форма может отличаться от простого коллайдера, но проходы и доступная поверхность должны совпадать. При rebuild меняется версия карты: routes, reservations, obstacle indexes и зависимые кэши пересчитываются или сбрасываются. Старый кэш с прежней шириной дороги способен ломать новый уровень без ошибки загрузки.

Разделяй tuning, пользовательские настройки и runtime-состояние. Validate/clamp выполняется на границе ввода данных. Сохранённые настройки получают версию и fallback для неизвестных полей, когда сохранение действительно нужно игре.
