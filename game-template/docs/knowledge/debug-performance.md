# Диагностика и производительность

Это порядок исследования дефекта и примеры полезных метрик. Хуки, профилировщик и системы NPC не реализованы в пустой сцене; добавляй их под конкретный сценарий. Бюджеты задаются в [GAME_BRIEF](../GAME_BRIEF.md).

## Воспроизведение до исправления

Запиши commit, устройство/браузер, параметры, seed/начальную раскладку, точные действия, ожидаемый и наблюдаемый результат. Укажи режим сборки, quality/DPR, длительность и прогрев. Сохрани небольшой trace или screenshot, если он объясняет симптом. Случайный один удачный запуск не опровергает редкий дефект.

Для коротких замеров сначала сравни одинаковую сцену; затем добавляй плотность и сложные случаи. Меняй одну подтверждённую причину за раз. Если симптом не воспроизведён, фиксируй это и добавляй диагностические данные, не объявляй соседнюю оптимизацию исправлением.

## Что измерять

| Метрика | Как трактовать |
| --- | --- |
| Интервал кадра, median/p95/p99, stalls | Общее ощущение; средний FPS может скрывать редкие задержки |
| Fixed steps и dropped seconds | Сколько работы симуляция догнала и сколько времени отбросила |
| CPU input/AI/physics/post-step/presentation/render | Где тратится CPU; время вокруг render не равно GPU time |
| Draw calls, triangles, visible/total objects | Цена отправки и геометрии; мало calls не исключает overdraw |
| Bodies, awake bodies, contacts, AI decisions | Цена симуляции; счётчики выбираются по API движка |
| Textures/geometries/programs, JS heap, активные timers/listeners | Тренд после прогрева и повторного lifecycle |
| Cold load, transfer, decode, first playable | Стоимость старта вместе с декодерами и обязательными ресурсами |

В Three.js `renderer.info` даёт счётчики отрисовки и ресурсов. При нескольких render passes за кадр настрой reset статистики так, чтобы учитывался весь кадр. Эти данные не являются измерением всей GPU-памяти. API: [WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html).

Для сравнения сохраняй исходные samples и способ вычисления percentiles. Не смешивай длительность разового fixed tick с суммой нескольких ticks кадра. Headless/software WebGL и desktop mobile viewport имеют отдельный статус в отчёте; производительность телефона проверяется на телефоне.

## Выбор следующего эксперимента

| Симптом | Что проверить первым |
| --- | --- |
| CPU растёт с количеством NPC | Число world steps, pairwise scans, частоту планирования, spatial index, allocations |
| FPS меняется при уменьшении DPR | Стоимость пикселей, прозрачных объёмов, postprocessing, shadow passes |
| Много calls при одинаковых объектах | Shared materials/geometry, instancing, material slots, группировку |
| Один эффект тормозит при близкой камере | Screen coverage, overdraw, число samples, DoubleSide и дополнительные проходы |
| Дёргается камера или модель | Смешение current и interpolated pose, порядок update, сброс previous/current |
| Объект исчезает после движения | Bounds, camera/frustum matrices, count/slot mapping, draw range |
| После reset растёт память | Listener/RAF, старые асинхронные результаты, texture/material owners, кэши |
| NPC стоит при свободном пути | Reason и blocker из текущего snapshot, stale reservation/route, условия FSM |

Это гипотезы для измерения. Например, чувствительность к DPR указывает на возможную стоимость пикселей, но сама по себе не доказывает конкретный GPU bottleneck.

## Диагностика поведения NPC

Снимок по actor ID полезнее огромного дампа мира. Для движущегося агента по потребности сохраняй `state`, `target`, `speed/targetSpeed`, `waitReason`, `blockerId`, `waitSeconds`, `noProgressSeconds`, reservation, возраст пути и число recovery. Причина ожидания должна подтверждаться фактом: занятым footprint, конфликтующим разрешением, сигналом или отсутствующим маршрутом.

Проверяй отдельно разрешённое ожидание и зависание после исчезновения причины. Для reservations тестируй release, удаление владельца, reset, rebuild, starvation и возобновление движения. Длительный seeded сценарий проверяет каждого агента: суммарный пробег может скрывать один навсегда остановившийся объект. Добавь перегруженный случай и освобождение препятствия. Не отключай collision safety ради прохождения проверки прогресса.

## Оптимизация и качество

Оптимизация подтверждается одинаковым до/после и сохранением нужного поведения. LOD, pooling и spatial partitions вводятся под измеренное ограничение. Кэш получает полный ключ параметров и правило инвалидации при rebuild. Любой пул/очередь имеет ёмкость и политику заполнения.

Режим графики может уменьшить DPR, тени, декоративные particles и samples. Он сохраняет информацию для принятия решения и игровой результат. Device type — эвристика стартового профиля; пользовательский выбор и замеры точнее названия телефона. Не обещай конкретный FPS по числу полигонов или успешной сборке.

## Как закончить проверку

Проведи релевантный unit/интеграционный сценарий, затем `pnpm check:full` для финальных тестов и сборки. Для изменённого изображения/ввода добавь браузерную проверку с фактическим WebGL и визуальный просмотр кадра. Для lifecycle повтори reset/смену сцены до стабильного тренда ресурсов. Частоты 30/60/120/144 FPS сравнивай для игровой логики с допустимым отклонением; фиксированный шаг не обещает детерминизм между платформами.

В отчёте различай тесты, build, browser surrogate, реальное устройство и ручное ощущение. При нативном падении worker или недоступной проверке сохрани ошибку и результат отдельного сценария; частичный прогон не становится полностью прошедшим suite. Выводы по накопленным отчётам CarWars перечислены в [sources](sources.md).
