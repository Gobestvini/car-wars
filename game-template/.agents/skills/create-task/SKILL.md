# Подготовка задачи для другой модели

Создай проверяемое задание на языке пользователя, которое исполнитель сможет выполнить без истории разговора. Главная работа автора — исследовать текущий проект, снять неоднозначность и ограничить объём, чтобы исполнителю не пришлось заново принимать архитектурные решения.

## Найди соглашения и контекст

Работай в текущем проекте, соблюдая его AGENTS.md. Прочитай `docs/tasks/README.md`, `docs/tasks/INDEX.md` и `docs/tasks/TEMPLATE.md`, если они есть. В проекте без системы задач создай минимальные аналоги: инструкции, индекс и шаблон с разделами ниже; сохрани существующую систему, если она использует другие пути или идентификаторы.

Исследуй только релевантные исходники, конфигурацию, тесты и документацию. Указывай существующие пути и имена функций/классов. Выясни текущее и требуемое поведение; не выдавай документацию за проверенное поведение кода. Запиши состояние проекта: ревизию Git и релевантные локальные изменения, если Git доступен; иначе дату проверки и отсутствие ревизии. Не изменяй реализацию при подготовке задания.

## Сформируй объём

Одна задача — одна цель с проверяемым результатом. Если нужны разные подсистемы, исследование, выбор архитектуры или последовательные этапы, выдели отдельные задачи и явные зависимости. Не придумывай необязательные улучшения или задачи вне запроса. Если пользователь просит только одну задачу, можно оформить ограниченный первый этап и назвать оставшуюся работу, не создавая лишние файлы.

Проверяемые факты, предположения и предложенные автором решения обозначай отдельно. Для безопасных деталей выбери разумный вариант и объясни его. При важном нерешённом вопросе подготовь доступную часть и оставь `draft`; уточнение запрашивай только если ответ влияет на результат. Невыполненные зависимости также не допускают `ready`.

## Напиши файл задачи

Используй проектный шаблон. Если соглашений нет, имя — `docs/tasks/TASK-NNNN-short-name.md`; номер на единицу больше максимального существующего номера среди файлов и индекса. Перед записью проверь, что файл не существует; никогда не перезаписывай чужую задачу. При просьбе обновить существующую задачу сохрани её ID и уже заполненный отчёт.

В задании нужны:

- ID, название, статус, даты, приоритет, проект, зависимости и рекомендация класса модели/уровня рассуждения с причиной. Не выдумывай цены и гарантии качества; точную модель называй при доступной проверенной информации или явном выборе пользователя.
- Цель, исходный запрос и наблюдаемое поведение до/после.
- Проверенный контекст и краткая карта конкретных файлов/символов.
- Область изменений, допустимые новые файлы, исключения и сохраняемое поведение.
- Требования: входы/выходы, релевантные состояния, ошибки и пограничные случаи.
- Конкретные шаги реализации с точками входа и интерфейсами. Избегай полного патча и длинных копий исходников; добавляй пример только для снятия неоднозначности. Допускай равноценный путь в заданных границах.
- Чеклист готовности и соответствующие автоматические/ручные проверки с ожидаемым результатом. Бери команды из текущего проекта. Не требуй новые тесты для каждой косметической правки.
- Предположения, открытые вопросы и условия остановки/обращения за решением.
- Готовое сообщение для передачи исполнителю с точным путём задачи и требованием заполнить отчёт.
- Отчёт исполнителя: результат, изменённые файлы, реальные проверки, невыполненные критерии, блокеры и итоговый статус. При подготовке пометь «Не выполнялась».

Для `ready` исполнитель должен знать, что менять, где начать, что сохранить и как проверить успех. Задачи с существенными неизвестными оставь `draft` или раздели на исследование и реализацию. Объём подробностей соразмерен сложности: краткая правка не требует длинного исследования.

## Проверь и зарегистрируй

Перечитай готовую задачу как исполнитель без истории чата. Проверь наличие файлов, символов и команд, непротиворечивость шагов и критериев, отсутствие незаполненных шаблонных полей. Это проверка задания, а не запуск реализации; не заявляй, что тесты приложения пройдены без фактического запуска.

Добавь ссылку, статус, приоритет, зависимости и рекомендацию исполнителя в индекс проекта. Статус в файле задачи — источник истины. Зависимые задачи переводятся в `ready` только после проверки завершения зависимостей и актуальности контекста.

Верни ссылки на созданные файлы, кратко перечисли результат, готовность к выполнению и сообщение для передачи. Не отправляй задание другой модели и не создавай отдельный чат без явной просьбы пользователя.
