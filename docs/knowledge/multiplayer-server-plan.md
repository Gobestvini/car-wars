# План мультиплеера CarWars: до трёх игроков

Дата исследования: 2026-10-14. Это предложение архитектуры и контракт серии TASK-0096–0101, а не отчёт о работающем мультиплеере. Первая задача проверяет решения прототипом; остальные остаются draft до независимой приёмки зависимостей.

## Запрос и границы

Пользователь хочет до трёх одновременно ездящих игроков на общей карте, серверную физику и серверный AI; просит изучить готовый игровой сервер. Предложенный первый релиз: свободная совместная езда с существующим трафиком, полицией, повреждениями, ремонтом и арестом. Это не новый соревновательный режим. Одиночная офлайн-игра сохраняется и использует тот же simulation core. Комнаты создаются по запросу; игрок может создать комнату, поделиться ссылкой или подключиться по коду. Общего публичного матчмейкинга, аккаунтов, чата, таблиц лидеров и постоянного хранения пока нет.

## Выбор технологий

Предварительный выбор автора: **Node.js + Colyseus + существующий cannon-es**, один simulation world на комнату. Colyseus предоставляет изолированные комнаты, лимит клиентов, таймер симуляции и рассылку состояния; см. [Room](https://docs.colyseus.io/room). Дельты Schema отправляются с отдельным patchRate: [State](https://docs.colyseus.io/state). Восстановление соединения описано в [Reconnection](https://docs.colyseus.io/room/reconnection). Это сетевой framework, физику/AI игры всё равно необходимо выделить из текущего кода.

Альтернативы для проверки TASK-0096:

| Вариант | Соответствие этому проекту и основание оценки |
| --- | --- |
| Colyseus | Предпочтителен для JS-кода, небольших комнат и готового lifecycle. Утверждение о лучшем соответствии — вывод автора, не результат benchmark. |
| Nakama | Имеет authoritative matches с фиксированным tick: [официальная документация](https://heroiclabs.com/docs/nakama/concepts/multiplayer/authoritative/). Проверить runtime/модули и возможность исполнения cannon-es без Node API. Богатый backend не требуется текущему запросу; отдельный physics process добавляет интеграцию. |
| geckos.io | Предлагает WebRTC data channels/UDP: [репозиторий](https://github.com/geckosio/geckos.io). Возможен выигрыш транспорта, но lifecycle, состояние и подключение потребуют своей работы; проверить ICE/NAT/порты. |
| Node.js + WebSocket вручную | Простая зависимость; автору придётся поддерживать комнаты, повторное подключение, ограничения и сериализацию. Сравнить как baseline, не выбирать только по минимальному числу пакетов. |
| Unity/Godot dedicated server или Rapier вместо cannon-es | Потребуется перенос/перенастройка текущей модели машины и физики. Не вводить без воспроизводимого доказательства непригодности существующей физики. |

Источники просмотрены 2026-10-14. Не фиксировать версии по памяти: прототип должен записать реальные совместимые версии Node, server, SDK, Schema/transport и lockfile, лицензии и способ запуска. Никаких обещаний бесплатного хостинга или доказанной производительности до измерений.

## Владение состоянием и interfaces

Браузер собирает клавиатуру/джойстик, рисует машины/город, HUD, камеру, звук и эффекты. Сервер владеет положениями, скоростью, столкновениями всех игроков и NPC, повреждениями/оторванными колёсами, AI/светофорами, розыском/арестом, предметами ремонта, разрушением props, спавном и seed карты. Скрытие вкладки, free camera или меню одного клиента не останавливают комнату.

Предложенные новые точки входа: `src/simulation/game-world.js` — createGameWorld(config); `server/rooms/driving-room.js` — сетевой адаптер; `src/network/protocol.js` — DTO/валидация; `src/network/room-client.js` — подключение; `src/network/snapshot-buffer.js` — представление. Названия можно уточнить в ADR, затем синхронизировать задания. Core имеет addPlayer/removePlayer/setPlayerInput/step/snapshot/dispose, не импортирует THREE, DOM, WebGL, GLTF и visual effects. Offline adapter вызывает тот же core локально.

Порядок substep: применить разрешённые команды на границе tick → ввод/AI → prepare всех физических тел → один world.step(1/120) → postStep → authoritative gameplay → snapshot/events. Статическая геометрия и материалы создаются один раз на world из общего data-only описания карты; не дублировать отдельные реализации бордюров и препятствий.

## Время и протокол

Исходные значения для проверки: physics 120 Hz с прежним STEP, scheduler 60 Hz с двумя substeps, AI 10 Hz, отправка input 30 Hz плюс немедленный neutral на blur, snapshots/patches 20 Hz. Частоты независимы. Bounded catch-up и счётчик debt обязательны; не увеличивать dt и не переносить browser rAF в сервер. При неподъёмной нагрузке остановить зависимые этапы и записать измерения/предложение; снижение качества или NPC до 10 не считается выполнением запроса.

Handshake: protocolVersion, buildId, roomId, playerId, roundId, mapSeed, map/config/generatorVersion и collision/map signature, serverTick/stepSeconds. Клиент подтверждает загрузку; до неё машина не получает ввод. Карта генерируется клиентом только по серверному контракту; несовпадение signature вызывает понятную ошибку, а не незаметную игру на другой карте.

Input: {roundId, seq, steer, throttle, brake}; конечные числа в согласованных диапазонах, bool для discrete actions; timestamp может служить только диагностике. Игрок определяется сессией, не входным playerId. Сервер назначает tick применения и возвращает lastProcessedInputSeq **на игрока**. seq — уникальный порядок команд, подтверждённый seq нельзя заново применять; пакет применяется как последнее допустимое состояние, неприменённые замещённые seq считаются потреблёнными при ack. Клиент не задаёт dt, transform, damage, wanted, spawn/repair result. Разрешённая команда respawn имеет отдельный requestId, cooldown и серверную проверку.

Snapshot: protocolVersion, roundId, tick, serverTime, players и actors с устойчивыми entityId/generation, position/quaternion/velocity/angularVelocity, steering, wheel pose/rotation/contact/slip/detachment, damage/lifecycle, per-player wanted/arrest/input ack; pickups, props, signal clock/phases. В wire DTO только числа/массивы/строки; не cannon bodies и не THREE objects. Полный snapshot включает состояние late join/reconnect, включая ранее разрушенные props и оторванные колёса. События имеют eventId/tick/actorId; повреждение/взрыв/ремонт/появление не дублируют эффект при повторной доставке. Долговечное состояние не должно зависеть исключительно от событий.

Серверные ограничения (проверить прототипом): input silence >250 мс сбрасывает газ/руль, включает тормоз; до 60 input messages/s, payload до 1 KiB, bounded queue. NaN/Infinity, чужая эпоха/seq, oversized/spam не падают в solver; систематический нарушитель отключается. Для output отдельный измеренный бюджет, лимит 1 KiB к snapshot не относится. Backpressure не копит бесконечную очередь старых состояний: ограничить транспортный буфер/отключить slow client, сохранить возможность получить full state.

## Несколько игроков и игровые правила

- maxPlayers=3, включая зарезервированные reconnection seats. Четвёртый получает «Комната заполнена». Гонку двух join на последнее место покрыть тестом.
- Машины игроков всегда physical в едином мире. Physical-zone NPC — объединение зон **всех** активных игроков, с hysteresis/contact retention и безопасным logical↔physical переходом. Spawn/obstacle occupancy учитывают все машины, прогноз траекторий и появляются безопасно для всех наблюдателей; нельзя despawn NPC как «невидимый», если его видит другой игрок.
- Общие civilian NPC, светофоры, pickups и props. Wanted/arrest/damage индивидуальны; событие нарушения атрибутируется конкретному playerId. Player-player удар даёт физические повреждения, сам по себе не вводит новое нарушение закона. Repair pickup выигрывает первый eligible по серверному tick, при равенстве — стабильный playerId; остальным не начислять ремонт.
- Полиция использует общий ограниченный пул: default базовая единица на активного игрока (в сумме до трёх), расширение по существующим wanted intensity profiles с явно установленным глобальным cap в ADR. Выбор цели: максимальный wanted, затем ближайший, затем playerId; текущая допустимая цель удерживается до смены её eligibility, чтобы не дрожать. Ни одна машина полиции не существует в нескольких независимых runtime. Арестованный или отключённый не получает новую погоню; оставшиеся играют.
- Respawn/R одного игрока сбрасывает только его damage/wanted/arrest и безопасно размещает его машину, не меняет общий seed и мир. Создание новой комнаты создаёт новую карту; кнопка общей смены карты в MVP не нужна.
- Disconnect: немедленно neutral/brake, тело остаётся общим физическим препятствием на reconnect grace=15 с. Возврат по закрытому токену сохраняет playerId/машину; после grace удалить тело/seat/target и запретить старому токену оживить другую сессию. Явный выход освобождает слот сразу; пустая комната с reservations закрывается после grace. Не журналировать reconnect secrets.

## Отклик клиента

Требование серверной физики понимается строго: online клиент не исполняет cannon solver и AI, не сообщает результаты своей физики. Удалённые машины интерполируются по серверному времени (исходный buffer 100 мс, адаптивно 50–150 мс); quaternion slerp, колёса/камера согласованы с chassis. Локальную машину можно отображать по самому свежему состоянию с ограниченной экстраполяцией скорости до 100 мс, косметической реакцией руля/индикаторов на ввод и плавной коррекцией. После teleport/respawn/нового roundId сбросить buffer; после >500 мс без state показать «Соединение нестабильно», прекратить экстраполяцию.

Это не гарантирует приемлемое управление через далёкий сервер. TASK-0096 и 0100 должны измерить input-to-visible-response. Если при RTT=100 мс целевой p95=200 мс не достигается или на RTT=150 мс езда непригодна, зафиксировать blocker и конкретный вариант локального **неавторитетного** prediction/reconciliation для согласования, не тайно возвращать физику в браузер. Полный lockstep и обещание bit-exact cannon между платформами исключены.

## Бюджеты и запуск

Предлагаемые acceptance budgets, не измеренные факты: на объявленном desktop/server hardware 3 игрока +102 civilians +активная полиция, 5 мин после прогрева: p95 полного substep ≤6 мс, p99 ≤8.33 мс; snapshot encoding учитывается отдельно и в общих scheduler costs, debt не нарастает. Замер 300 NPC — стресс с явным результатом, не обязательный default. Wire target ≤150 KiB/s outbound на клиента при default NPC и полной репликации, считать фактические байты с framing; стабилизированная память последних двух минут растёт не более чем на 10% после GC с описанным методом. Нельзя объявлять успех без hardware, версии runtime, seed, NPC counts, сырого артефакта и методики.

Первый релиз: один Node process, комнаты изолированы, конфиг максимального количества комнат/подключений и graceful shutdown. Не обещать число комнат на CPU без load test; workers/sharding/Redis только при измеренной необходимости. Подготовить self-host запуск и Dockerfile/compose без платных сервисов, пример reverse proxy для HTTPS/WSS, VITE_GAME_SERVER_URL и серверные env отдельно, health/readiness. Автоматический публичный deploy не входит в подготовку или исполнение без конкретного запроса/доступа.
